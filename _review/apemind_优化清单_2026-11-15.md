### 2.2 提示词正文新增的四条硬约束

原提示词的合规红线写得好（合规红线 + 证据纪律两段），但缺四件产品化必需的东西。新版正文 1425 字，加了：

**① 分值问题分三层，堵住「问得分」这个最高频问题**

原文只写「不得输出评分多少」，客户一问「这家能得多少分」就只剩拒答。现在分层：

- 可答：评分标准原文位置、分值区间、计算规则
- 可答：本标包分值权重构成（前附表之六）原文
- 不可答：某投标人的技术得分/商务得分/总分/排名——库里没有专家实际打分，给数字就是编造

**② 「没有」必须被证明，不能靠没搜到就断言**

这是产品化最容易翻车的地方。语义检索是 top-N 截断，返回空不等于不存在。现在明确要求：断言「库内没有」之前必须做逐行精确扫描且 `coverage=complete`，覆盖不完整只能说「未扫完，不能断定」，并写清检索范围。这条直接对应本轮已落地的 `/api/grep` 端点。

**③ 机器判定优先，不重算**

46 条有确定性引擎，助手若自行推理，同一个问题在「工作台」和「问助手」会给出两套结论——这是对客最危险的分叉。现在规定：有引擎结果就引用并带规则集版本与 sha；引擎给 UNCERTAIN 就说证不足并指出缺哪个字段（读 `blocked_by`）；引擎给 NEED_HUMAN 就说只能人判。

**④ 先锁批次与标包，再检索**

原文只有一句「看文件名前缀识别标包」。155 份文件同名严重，实际不够用。现在改为检索前必须先确认批次（152507/1525K1）+ 标包号，确认不了就声明「未锁定标包」。

### 2.3 提示词还没解决的两条

1. **没有可机读的引用结构**。现在输出是四段中文（结论/依据/待澄清/需人工判定），人读没问题，但前端要做「点击跳到原文行号」拿不到结构化引用。要产品化建议改成每段附 JSON：`{doc, section, line, handle}`。这一步要改输出协议，需和前端口径一起定。
2. **没有版本自证**。答案里不带规则集版本与 sha，事后无法回答「这个结论是哪版规则出的」。已在提示词里要求引用引擎输出时带 sha，但还没做成强制字段。

## 3 平台函数：已发布 v4 的三项加固

`sgcc-rule-judge` v3 → v4，本地回归 96/96 逐条一致后发布。

### 3.1 三项改动

**① 未知 `rule_ids` 不再静默返空（最要紧的一项）**

改前实测：传 `rule_ids: ["GW-HB-FJ-999"]`，函数返回 `status: succeeded`、`total: 0`、`counts` 全 0、`decided: 0`。

这是最难发现的一种假绿——调用方（尤其把规则号写死在配置里的前端或上层函数）会拿到「零命中且成功」，读起来像「这个标包没有否决情形」。规则号写错是调用方 bug，必须炸出来。

改后：

```
status: failed
ValueError: 未知的 rule_id / 行号：GW-HB-FJ-999。本规则集 V2 共 46 条，
            可用取值见 rule_set 字段或 GET 函数说明
```

**② 单条规则异常不再连坐全部 46 条**

`run_rule()` 内部只兜 `NeedMissing` / `KeyError`。类型、属性、除零这类异常会抛穿 `main()`，整个请求失败——一条规则写错，其余 45 条的结论一起拿不到。规则表后续由业务方维护，这个爆炸半径不能留。现在单条异常降级为 `UNCERTAIN` + 写进 `notes`，其余规则照常。

**③ 新增 `blocked_by`：把「16 条待澄清」按缺什么聚合**

改前只有 `uncertain_rows: [1,2,3,5,12,21,...]`，前端逐条列出来像 16 个互不相干的问题。实际是 31 个字段卡住 16 条。客户看到的差别很大：前者是「系统看不出东西」，后者是「补这 8 个数能再判 8 条」。

新增结构（宜昌实跑，平台侧）：

```json
blocked_by: [
  {"field":"bid.qualification_fields","side":"bid","rows":[30,31],
   "hint":"投标文件没抽到这个字段：重抽该字段，或人工核对投标文件对应页"},
  {"field":"tender.avg_price_threshold_rule","side":"tender","rows":[46],
   "hint":"招标文件未给出该参数（或该表未结构化）：只能人工对照原文补录，补不上就只能是待澄清"},
  ...
]
```

`side` 四档：`bid` 投标侧 / `tender` 招标侧 / `legal` 法规名单 / `platform` 库外数据。

另加 `warnings`：未传基准侧、未传 `peer_facts`、`bid_fields` 与 `facts` 同时传（同名字段会被覆盖）。这三类输入降级过去是静默的，现在会明说。

## 4 产品化前的三个硬问题（需要拍板）

### 4.1 助手还没发布

`agent access get` 当前：`enabled: false`、`platform_access: false`、`audience: org`。

配置已经就绪，但对外可用还差发布动作。给国网用户还要决定：走组织内账号，还是走公开链接（`--public on` 需 `--confirm`）。这属于交付形态决定，未擅自执行。

### 4.2 受审侧「一家一库」在真实场景不可运维

6 家投标人 = 6 个知识库，库描述里自己写了原因：「多家同库时 top N 会被别家的块挤占，本家文件排不进来，字段抽取会随机失败」。

真实标包动辄 20–50 家投标人。按现在这个分法，一个标包就是 50 个库，一年 14 个分标就是 700 个库——运维不可承受，且每次投标人变动都要建库、挂库、配权限。

可选方向（需评估后再定）：

- A. 按标包一库 + 文档级 `bidder` 元数据，检索时按 bidder 过滤（依赖平台是否支持 metadata filter）
- B. 保持一家一库，但由上层自动建库挂库（把运维成本转成平台调用）
- C. 按标包一库 + 每家一个独立 `collection` 分区（若平台支持子分区）

### 4.3 BFF 用的是 owner 全权凭证，不能给客户

页面背后是 `sgcc_bff.py` 调 CLI，用的是当前登录账号（`tgotest`）的会话。该账号 scope 含 `knowledge_base.write`、`function.write`、`organization.manage_settings`、`organization_member.remove`。

演示期同机可控还好；产品化交付国网时必须换成专用只读身份 + 独立 API Key，否则等于把组织管理权限一起交给客户侧的任何一次越权调用。这是产品化必须做的一件事，与提示词无关但优先级更高。

## 6 平台性能：先分段，再动手

性能这件事必须先量清楚再改。本轮量下来，结论和直觉相反：**函数本身不慢，慢在往返次数**。

### 6.1 分段读数（正常网络期实测，2026-11-15 20:5x–21:0x）

| 段 | 读数 | 说明 |
|---|---|---|
| 函数自报耗时（46 条） | 245 ms | 平台侧 |
| 函数自报耗时（只跑 1 条） | 244 ms | 出参 2.6 KB vs 35.4 KB |
| CLI 进程启动 + 读凭据 | 131 ms | `auth status`，不联网 |
| CLI 单次调用 wall | 2.1–3.4 s | `function invoke` 端到端 |
| BFF 首次请求（旧代码） | **6096 ms** | `/api/judge/by-code` 未命中 |
| BFF 二次请求（旧代码，120s TTL 内） | 12 ms | 命中内存缓存，但 TTL 只有 120s |
| TLS 握手 | 750–790 ms | 每次新进程都要重做 |
| HTTP 到 `/api/v2/health`（404） | 1.19–1.23 s | 握手之后服务端仍占 0.4s |

两个决定性读数：

1. **1 条规则和 46 条规则都是 245 ms**，出参差 13 倍。说明这 245 ms 是平台每次调用的**固定开销**
   （沙箱、框架、模型构造），不是逐条计算。所以「优化判定逻辑」这条路没有收益，
   函数侧唯一能做的是别为了省时间裁规则。
2. **CLI 进程本身只占 131 ms**，真正的大头是每次都要重新做一遍 TLS 握手（约 750 ms）
   加服务端处理。CLI 是一次性进程，用完即走，天然没法复用连接。

### 6.2 因此能优化的是「次数」，不是「单次」

判定是纯函数，输入是静态文件（`_judge_in_<代号>.json`），
**同一份输入永远算出同一份结论**。这类计算不该每次都去问平台，应该物化。

已落地（`sgcc_bff.py`）：

| 改动 | 作用 |
|---|---|
| `_judge_snap/<代号>.json` 判定快照 | 输入指纹一致 → 直接读盘，**1 ms**（HTTP 全程 13–15 ms） |
| 指纹校验（sha256 前 16 位 + 版本号） | 输入换了、对不上就重算，不拿旧结论冒充新结论 |
| 原子替换（写 `.tmp` 再 `os.replace`） | 并发读不会读到半个文件 |
| 启动预计算 `presnap()` | 六家串行算一遍，只算缺的 |
| `/api/judge/snap` 体检端点 | 逐家报「快照在不在、指纹对不对、生成时间」 |
| `POST /api/judge/refresh` / `?refresh=1` | 显式重算，演示时想现场看一次真调用时用 |
| 网络闸门 | 一家判定为网络不可用就停掉剩余，避免启动期空转十几分钟 |

效果对比（同一家、同一份输入）：

| 场景 | 旧 | 新 |
|---|---|---|
| 首次（无缓存） | 6096 ms | 6096 ms（无快照时仍走真调用） |
| 缓存过期后（>120s） | 6096 ms（回到慢路径） | **1 ms** |
| 快照命中 | — | **1 ms**，且与 TTL 无关 |

也就是说：旧代码只有「2 分钟内第二次点击」是快的，冷场就要再等 6 秒；
新代码除首次生成外恒为 1 ms。

### 6.3 顺带修掉一个单点故障

排查过程中抓到的真实故障（21:10–21:14）：本机 `http_proxy` 指向 127.0.0.1:53322 的本地代理，
**代理挂掉后 CLI 全部 `network_unavailable`，而同一时刻 curl 直连是通的**。
BFF 把自己 shell 里的代理设置继承给了子进程，于是可选加速件变成了必经单点。

改法不是简单剥掉代理（有些环境反过来只有代理能通），而是**双路兜底**：
先直连（30s 内不通用完），失败再退回原环境走代理；两条都不通才算失败。
`_stats.proxy_fallbacks` 会记下走了几次兜底。

顺带纠正一条我自己先前写错的判断：排查时看到「六路并发全失败」，一度记成
「CLI 不能并发」。实际那十几分钟正是代理不可用期，并发这条路没被证伪。
`presnap` 仍默认串行，理由改成"不值得为省十秒去赌未验证的并发"，而不是"并发不行"。

### 6.4 还没做的两件（都卡在同一处）

- **连接复用**：要做到每次调用省掉 750 ms 的 TLS，只能让 BFF 直连 HTTP 并保持长连接。
  这需要一个 API Key，而创建 Key 要 `apemind auth login --scope apikey.write`，
  属于交互式授权。顺带能一并解决第 4.3 节那个 owner 全权凭证问题——两件事同一次动作。

### 7.2 两个独立原因，别混

| # | 原因 | 证据 | 结论 |
|---|---|---|---|
| A | `spec.capabilities.functions: {}` 只授出 `function.use`，**不把函数注册成原生工具** | 身份权限 `functions: "use"`；工具清单里没有该函数；`agent options.levels.functions` 只有 `none/use` 两档，没有按函数粒度的授权项 | 平台设计如此，函数只能经 CLI 调 |
| B | `spec.policy.write_confirmation: true` 让 `run_command` 先弹审批卡；**无头调用没有人点** | 同一 turn 三次 `no decision arrived in time`；关掉后同一命令立刻 exit 0 | 无头/API 场景的硬死结 |

B 是这次的真故障，A 是必须接受的架构前提。

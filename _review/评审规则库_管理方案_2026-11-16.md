# 评审规则库管理 · 落地方案（2026-11-16）

面向客户提出的「评审规则库要能自己管」。本文只回答三件事：**现在是什么形态、客户能管到哪一层、页面怎么摆**。

---

## 一、先分清：现在的"规则库"是四层，不是一份

| 层 | 载体 | 条数 | 谁该管 |
|---|---|---|---|
| L1 规则台账 | `国网Demo_专家评审规则库_V1.json` | 46 条 | **客户** |
| L2 规则范围 | 同上 `rule_groups` | 4 组（仅 RG1 已结构化） | **客户补录** |
| L3 可执行分派表 | `国网Demo_规则可执行化_46条分派表_V2.json` | 46 条 | 交付方 |
| L4 运行时引擎 | `sgcc_fn_rule_judge/main.py`（规则以 JSON 字符串内嵌） | 46 条 | 交付方，且只能重发版本 |

L1 与 L3 靠 `rule_id` 对齐，字段互补（实测）：

| L1 台账独有 | L3 分派表独有 |
|---|---|
| `chapter` 章节出处<br>`batch` / `packages` 适用批次标包<br>`representative_docs` 代表文件<br>`source` 出处<br>`evidence_level` 证据等级<br>`ai_can` / `ai_cannot` 能做什么/不能做什么<br>`confirm_role` 确认角色<br>`version_diff` 版本差异标记<br>`status` 台账状态 | `exec_path` 执行路径<br>`needs` / `optional_needs` 字段依赖<br>`check` 判定式（受限 DSL）<br>`states` 状态映射<br>`conclusion_ceiling`<br>`human_gate` 人工闸门<br>`external_source` 外部源<br>`signals` 提示信号<br>`why_this_path` / `upgrade` |

**关键判断**：客户管 L1、L2；L3、L4 必须由交付方维护。原因不是权限，是有过两次真实事故——
行 10 拿未含税行价比含税限价，会漏判宜昌；行 11 用 0.01 元容差，把六家投标人全部误判。
这类错误改完表面正常，只有跑基线才看得见。让客户手改 `check` 等于把这两类事故的复发权交出去。

## 二、现状缺口：最缺的不是页面，是"没人核过"

| # | 缺项 | 现状（实测） | 影响 |
|---|---|---|---|
| 1 | 业务方核对 | 46 条 **全部 `status=CANDIDATE`**，`evidence_level` 只有一种："【T】AI 逐条回读，尚未经业务方对照原文核对" | **0 条被确认过**，台账可信度停在 AI 自述级 |
| 2 | 写回通道 | 台账是本地 JSON 文件，改完要重打包、重发函数 | 客户无法日常维护 |
| 3 | 变更审计 | 只有一个 `status` 字段，没有"谁 / 何时 / 从什么改到什么 / 为什么" | 出问题无法追溯 |
| 4 | 版本对比 | `meta.change_log` 靠手写，`version` 与 `sha` 无联动 | 改了规则忘改版本号，就出现同名不同内容 |
| 5 | 影响面回归 | 有 `judge_local_regress.py` + `_judge_snap`（六家基线），但没串成流程 | 改一条，不知道会动哪几家哪几行 |
| 6 | 补录队列 | RG2（正文明确触发否决的条款）、RG3（K1 特有高价/不平衡报价）、RG4（公告资格条件同源条款）三组只写了"本轮未逐条结构化" | 客户不知道要补什么、补到哪 |

缺口 1 是真正的业务工作量：把 46 条从 CANDIDATE 推到 CONFIRMED，需要业务方逐条对照招标文件原文。**管理面的第一价值是让这件事能干**，而不是把已有数据摆得更好看。

## 三、载体：用平台的 dataset，不自建库

平台已有完整的 dataset 能力（`apemind dataset *`）：
`create` / `item add|update|delete` / `--revision N` 并发控制 / `version diff` / `import` / `export` / `eval`。

映射方式：

| 规则概念 | dataset 字段 |
|---|---|
| 一条规则 | 一个 item |
| `rule_id` | `external_id`（按 ID upsert，天然幂等） |
| `rule_text` | `question` |
| `category` / `subcategory` / `exec_path` / `status` | `tags`（用于筛选与统计） |
| 其余全部字段 | `metadata`（自由 JSON） |
| 规则库版本 | dataset version（`version diff` 可直接出改动清单） |

好处：版本、并发锁、导入导出、评测全部复用平台，不引入新的存储与运维。

### 3.1 三个前提已实测（2026-11-16，脚本 `_review/verify_dataset_rules.py`）

| 前提 | 结论 | 实测凭据 |
|---|---|---|
| T1 `metadata` 能否原样吃下 `check` 嵌套与附加参数键 | **PASS** | 用 FJ-032（跨行稀有算子 `group_dup_le`/`group_no_overlap`）与 FJ-010（附加键 `fallback_total`/`key`/`amount_basis`/`amount_basis_why`）两条写入再读回：`全等=True`、`check=True`、**丢键=无** |
| T2 容量上限 | **PASS** | `max_items=5000`、`max_versions=50`、`metadata_bytes=8192`、`content_bytes=20MB`、`question_chars=16000`、`max_tags=20`；导入格式 csv/xlsx/jsonl，导出 csv/jsonl |
| T3 `version diff` 粒度 | **PASS（条目级）** | 返回 `summary{added/deleted/modified}` + `items[{kind, before, after}]`，**没有 `changed_fields`** |

T3 的实际影响：升版时要的「字段级改动清单」，平台不给，得拿 `before`/`after` 两份全量在页面上自己比。
不难（前端 diff 即可），但不能对客户说"平台直接给字段级差异"。

**metadata 体积实测**（按 8192 上限）：46 条中最大 2994 B（FJ-013，占 37%）、中位 1767 B（22%）、零条超限。
还有约 2.7 倍余量，够加审计字段（reviewer / reviewed_at / status_history）。

### 3.2 发版还会附一个 `content_hash`

`dataset version publish` 的返回里有 `content_hash`（如 `7832aa2d…`），是整版内容的指纹。
这正是现在 `RULE_SET_SHA = "e80fd7b21492dc44"` 手写常量的替代品——**升版时不必再人工算 sha**，
直接取发版返回的 hash 写进规则库元信息即可，两边永远一致。

### 3.3 客户日常维护路径：Excel 进、Excel 出（已实测）

这条比做页面编辑更贴合客户习惯，也已验证可用：

```
1. 导出：apemind dataset export <DS_ID> --output 规则库.xlsx
2. 客户在 Excel 里改 [规则原文 / 状态 / 出处 / 适用范围]，不动 check 列
3. 回导：apemind dataset import create <DS_ID> --file 规则库.csv \
           --map external_id=规则号 --map question=规则原文 \
           --map metadata=元数据 --mode upsert_external_id
         （先出预览：summary 与 errors，确认后再 --commit / preview_token 提交）
4. 发版：apemind dataset version publish <DS_ID> --revision <当前> --note "…"
5. 回归：跑六家基线，看影响面（见 P2）
```

实测要点（用 2 行 CSV 跑通）：
- `--mode upsert_external_id` 按 `external_id` 匹配，预览返回 `added:1 / updated:1 / errors:0`；
- **Excel/CSV 里的 metadata 列会被自动解析成 JSON 对象**（读回是 `dict`，不是字符串），
  所以整条规则（含 `check` 嵌套）能经 Excel 往返而不丢结构；
- `--encoding gb18030` 可读 Excel 直接导出的中文 CSV，不必先转 UTF-8。

### 3.4 平台侧两个已知限制

- **`dataset update --status archived` 需要 `dataset.write` scope**，当前账户没有（能建集、能写条目，不能改状态）。
  验证过程留下的 3 个 `SGCC-规则库-VERIFY-*` 数据集需在控制台手工归档。
- **`version publish` 走乐观锁**：同一数据集连续发版会报 `conflict`，脚本重跑需加 `--fresh` 新建数据集。
  生产上这不是缺陷（本来就该一次一版），但演示脚本要注意。

## 六、必须跟客户讲清的两条边界

1. **规则库改的是"条款与适用性"，不是"判定逻辑"。**
   台账里改 `rule_text`、`batch`、`version_diff`、`status` 都是安全的；
   改 `check`（判定式）、`needs`（字段依赖）、`exec_path`（执行路径）会改变判定结果，
   必须走"改 → 跑六家基线 → 看影响面 → 发布"这条路，不能页面上直接存。

2. **`status=CONFIRMED` 不等于"该条款可自动否决"。**
   它只表示业务方对照原文核对过。结论上限恒为 `CANDIDATE`，
   法定认定权在评标委员会——这条红线在台账、页面文案、对客话术里都要一致。

## 七、待确认

1. **范围**：客户说的"评审规则库"只指 46 条否决情形，还是也包括评分标准（商务 23 项 / 技术 16 项）？
   后者目前**没有引擎**，只有技能里的描述文本，若要管需要另建一套结构（分值、去极值规则、主观项归属）。
2. **置位权**：谁有权把 CANDIDATE 置为 CONFIRMED——物资专责、评标专家，还是必须评标委员会？
   这决定 P1 的角色模型。
3. **维护形态**：客户是愿意在页面里逐条改，还是更习惯"导出 Excel → 改完导入"？
   dataset 两种都支持，但页面设计差别很大（B 型 vs A 型 + 导入区）。
4. **多批次**：152507 与 1525K1 的条款有版本差异（行 46 已标 `version_diff=true`），
   规则库是按批次各存一份，还是一份带 `batch` 维度做视图？前者简单、后者好维护，需拍板。

# 规则引擎可配置 · 基于 apemind 的实现路径（2026-11-16）

> 所有能力结论都来自实测（临时探针函数 `tmp-probe`，用完已删除），不是文档推断。
> 探针记录见本文第 2 节的「怎么测的」一栏。

---

## 一、先界定：可配的是「规则内容」，不是「判定逻辑」

「规则引擎可配置」这句话有两种理解，差别很大：

| 理解 | 能否做到 | 说明 |
|---|---|---|
| A. 规则内容可配：条款文本、适用范围、字段依赖、阈值、判定式（用**已有算子**） | **能，且不用改代码** | `check` 本质是 JSON 数据，算子白名单固定 |
| B. 判定逻辑可配：新增算子、新语义、新翻译规则 | **不能纯配置**，必须发版 | 算子实现、字段翻译（`build_bid`）是代码 |

所以对客表述应当是：**在受限 DSL 白名单内，判定式可以完全由业务侧配置；超出白名单才走发版。**
这已经覆盖绝大多数真实变更——本次 46 条里 25 条是机器可判，全部用 15 个算子 + 8 个函数就够了。

---

## 二、现状为什么不可配：三处硬编码

`sgcc_fn_rule_judge/main.py`（由 `build_judge_fn.py` 生成）里：

```python
RULES_V2   = json.loads(r"""{"meta":…,"rules":[…46 条…]}""")   # 规则编译进源码
RULE_SET_VERSION = "V2"                                        # 手写常量
RULE_SET_SHA     = "e80fd7b21492dc44"                          # 手写常量
```

后果：改一条规则 = 改分派表 JSON → 跑 `build_judge_fn.py` 重新生成 main.py → `function apply` 发新版本。
客户改不了，交付方每次都要走一遍打包发布。

## 三、平台实际给了什么（实测）

探针函数里 `print(dir(ctx))` 与逐方法取签名得到的真实能力：

| 能力 | 签名 / 形态 | 实测结果 |
|---|---|---|
| `ctx.search` | `(query, knowledge_base_ids=None, *, limit=10) -> list[dict]` | **可用**，命中返回 `rank/score/content/source/recall_type/metadata/recommended_read/knowledge_base_id` |
| `ctx.api` | `Api(base_url='http://apemind.internal', key='sk-…')`，有 `get/post/put/patch/delete/request/session` | 客户端可用；但 **GET `/api/v2/datasets/…` 返回 403 `dataset_permission_denied`** |
| `ctx.state` | `dict` | **跨调用持久化**：连续两次 invoke，`probe_hits` 从 1 累到 2 |
| `ctx.invoke` | `(function: str, input: dict) -> dict` | 可调本组织其他函数（算子运行，受并发槽限制） |
| `ctx.llm` / `ctx.chat` | `llm(prompt, system, output, model)` / `chat(messages)` | 可用，`output` 传 Pydantic 模型可拿结构化输出 |
| `ctx.connect` | `Connect(org_id=…)` | 走组织连接（外部系统），需授权 |
| `ctx.step` | `(name, *, detail)` | 轨迹分组，`detail` 上限 2KB |
| 大入参 | `Input.rules: List[Dict]` | **46 条规则 43,799 字节完整传入**，`n=46`、`check` 结构完好，全程 278ms |
| 接口变更闸 | — | 改 `Input`/`Output` 字段会报 `breaking_change`，必须显式 `--accept-breaking` 才发布 |

## 四、四条路径，两条不可行

| 路径 | 机制 | 函数要重发？ | 判定 |
|---|---|---|---|
| **A. 规则随入参注入** | `Input.rules` 传入规则表；调用方（BFF/页面）负责取规则 | 否 | **推荐主路径**（已实测 43.8KB 通过） |
| **B. 规则存知识库，函数 `ctx.search` 读** | 函数配 `access.collections=allowlist`，一条规则一文档 | 否 | 可做但不推荐：`search` 是 top-N 语义检索，**不能保证取全 46 条**，判定要求"一条不漏" |
| **C. 规则存 dataset，函数 `ctx.api` 读** | — | — | **不可行**：403 `dataset_permission_denied`。函数的 `permissions` 只有 `functions`/`knowledge_base` 两个维度，没有 dataset |
| **D. 规则变更走函数版本发布** | `build → apply` | **是** | 保留给"改算子/改翻译"这类真代码变更 |

路径 C 被否掉这件事很重要——它意味着**dataset 与人、函数与 KB 是两条不通的路**：
dataset 适合"人维护 + 版本管理"，KB 适合"函数检索"，两者不能互相替代。

## 五、推荐架构：三层，按变更频率分

```
┌─────────────────────────────────────────────────────────────┐
│ 配置面（客户可改，不碰代码）                                    │
│   dataset「规则台账」 ← Excel 导入/导出、版本 diff、content_hash │
│     ├ 条款文本 / 章节出处 / 适用范围 / 状态                     │
│     ├ needs / optional_needs（字段依赖）                       │
│     ├ check 判定式（只用白名单 15 算子 + 8 函数）                │
│     └ 阈值参数（tolerance_yuan、amount_basis、fallback_total…） │
└──────────────────────────┬──────────────────────────────────┘
                           │ 读取（BFF 或页面）
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 注入面（每次调用带上）                                          │
│   function invoke sgcc-rule-judge --field rules='[…]'        │
│                                  --field rule_set_sha=…      │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ 代码面（交付方发版，变更需过回归）                               │
│   算子实现（evaluate 的 15 个 op）/ 字段翻译（build_bid）        │
│   / 结论状态机 / 输出契约                                      │
└─────────────────────────────────────────────────────────────┘
```

关键点：**判定式（`check`）在配置面**。这是 DSL 的全部价值——业务改判定式不必等发版。
但因为它会改变判定结果，配置面必须挂一道回归闸（见第七节），不是"随便改"。

## 六、最小改造：给函数加两个可选入参（v5）

改动很小，且**向后兼容**——不传就走内嵌 V2，现有调用方（BFF 六家页面）零影响。

```python
class Input(BaseModel):
    section_no: str = ""
    bidder: str = ""
    tender_fields: List[Dict[str, Any]] = []
    bid_fields: List[Dict[str, Any]] = []
    facts: Dict[str, Any] = {}
    peer_facts: List[Dict[str, Any]] = []
    rule_ids: List[str] = []
    # ↓ 新增两个可选入参
    rules: List[Dict[str, Any]] = Field(
        default_factory=list,
        description="外部规则表；不传则使用内嵌 V2。传了则以传入为准")
    rule_set_sha: str = Field(
        default="",
        description="外部规则表的指纹；与内嵌不一致时在输出里标注来源，便于追溯")


# main 里
def main(inp: Input, ctx: Context) -> Output:
    if inp.rules:
        rules, source, ver = inp.rules, "input", inp.rule_set_sha
    else:
        rules, source, ver = RULES_V2["rules"], "embedded", RULE_SET_SHA
    # 之后 evaluate 全部用 rules，不再直接读 RULES_V2
```

`Output` 增一个字段，让每次调用都能自证"这批结论是哪份规则算的"：

```python
class Output(BaseModel):
    …                       # 原有字段不动
    rule_source: str        # "embedded" | "input"
```

这样：
- 不传 `rules` → 行为与现在逐字节一致（回归基线不受影响）
- 传 `rules` → 客户改的规则立即生效，**函数不重发**
- 输出带 `rule_source` + `rule_set_sha` → 事后能回答"这条结论是哪版规则出的"

代价：`Input`/`Output` 加字段属 `breaking_change`，发布时要带 `--accept-breaking`（实测会拦）。这是一次性的。

## 七、配置面必须挂三道闸，否则会假绿

`check` 变成可配之后，最危险的不是"配不出来"，是**配错了还报绿**。已知两次真实事故都在这一层：

| 事故 | 现象 | 只有回归能发现 |
|---|---|---|
| 行 10 含税口径 | 拿未含税行价比含税限价 → 漏判宜昌 | 单看返回 `RESPONDED` 一切正常 |
| 行 11 容差 0.01 | 把"元取整"当成小数点错误 → 六家全误判 | 单看某一家也"有结论" |

所以配置面要配三道闸：

1. **保存闸**：改 `check` 时不校验表达式合法性 → 必须校验算子是否在白名单、`needs` 引用的字段名是否存在。
2. **回归闸**：任何 `check` / `needs` 变更，自动跑六家基线（`_judge_snap` + `judge_local_regress.py` 已有），
   输出"哪几家、哪几行、状态从什么变成什么"，差异未确认不得发版。
3. **指纹闸**：`rules` 的 sha 与输出里记录的 sha 必须一致，防止"页面看到的是新规则、跑的是旧规则"。

第 3 道闸现在已经有一半：`_judge_snap` 用 `sha256(raw)[:16]` 做指纹校验。规则改到 dataset 之后，
dataset 发版返回的 `content_hash` 可以直接当这个指纹（已实测返回该字段），不必再手算。

## 八、`ctx.state` 能用在哪（可选优化）

`ctx.state` 跨调用保留，可以用来缓存"已解析的规则表"，避免每次调用都重新解析 43KB JSON。

但**不建议默认开启**，理由：
- 解析 46 条 JSON 只有毫秒级，缓存收益不明显；
- 缓存键必须是规则 sha，一旦 sha 传递出错，就会拿旧规则判新数据——这正是假绿的最短路径。

真要用，只能是"sha → 解析结果"的映射，且 sha 不匹配立即重算。收益小、风险大，先不做。

## 九、分期

| 期 | 内容 | 交付物 |
|---|---|---|
| P0 | 函数加 `rules` / `rule_set_sha` / `rule_source`（向后兼容）；BFF 改为从规则源读表后注入 | 改一条规则不再需要发版，可用 CLI 演示 |
| P1 | 规则源搬进 dataset（Excel 进出、版本 diff、content_hash）；页面只读台账 | 客户能自己维护条款与阈值 |
| P2 | 配置面加三道闸（保存校验 / 六家回归 / 指纹一致） | 客户可以自主改 `check`，且改错会被拦住 |
| P3 | 新算子需求走发版流水线（`build_judge_fn.py` 自动化） | 判定逻辑扩展有正规通道 |

## 十、必须跟客户说清的两条

1. **"可配置"不等于"随便改"。** 改条款文本、适用范围、阈值是安全的；改 `check` 会改变判定结论，
   必须过回归闸。把这两类混在一起讲，客户第一次改判定式就会出事故。
2. **结论上限不变。** 无论规则怎么配，输出仍是 `CANDIDATE`，机器不给否决结论。
   配置能力提升的是"规则维护效率"，不是"判定权限"。

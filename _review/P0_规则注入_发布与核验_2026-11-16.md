## 一、先修的一个隐患：生成器滞后于线上 v4

准备发布时跑回归，六家全不一致。定位结果不是 P0 改造引入的，而是
`build_judge_fn.py`（生成器）落后于线上手改过的 v4 —— 任何人跑一次 build 都会冲掉这些能力。

| # | 漂移点 | 影响 |
|---|---|---|
| 1 | `class BlockedBy` 整段缺失 | 出参没有 `blocked_by`，前端只能看到 16 个孤立行号 |
| 2 | `Output.blocked_by` / `warnings` 缺失 | 同上，且失去"缺哪个字段、该谁补"的聚合 |
| 3 | `rule_ids` 未知值不报错，只做过滤 | 传错规则号 → `total=0` 且 `succeeded`，最典型的假绿 |
| 4 | `run_rule` 没有 try/except | 一条规则写错 → 整请求失败，其余 45 条结论一起拿不到 |

四处已全部回填进 `build_judge_fn.py` 模板。回填后 `diff v4 vs 生成结果`，
剩余差异 **105 行，全部是 P0 的预期新增**，无一处反向删除：

```
删除行仅 6 行，且都是被 P0 改写的那几行：
- rules = RULES_V2["rules"]                     → 改为按来源分支
- known = {... str(r["row"]) ...}                → 改为 r.get("row")
- "...RULE_SET_VERSION..."                       → 改为 rule_set（外部版本名也要进报错）
- rule_set=RULE_SET_VERSION, rule_set_sha=RULE_SET_SHA  → 改为变量
```

## 二、函数改造（P0 第一半）

生成器 6 处改动 + 模板回填 4 处，重新生成 `main.py` 83654 字节。

- `Input` 新增：`rules: List[Dict]`、`rule_set_version: str`、`rule_set_sha: str`（均可选，默认空）
- `Output` 新增：`rule_source: str`（`embedded` / `input`）
- 指纹口径：`sha256(json({"meta":{version,n},"rules":slim(rules)}))[:16]`，
  slim 只留 15 个 KEEP 字段，与生成器同源（模板里由 `{keep_fields}` 注入，单一真相源）
- 传入指纹与实算不符 → **只写 notes 留痕，不阻断判定**
- 补一条定向提示：未传 `rule_set_version` 时指纹按 `EXTERNAL` 算，与 `RULE_SET_SHA` 天然不同，
  **这不是规则被改** —— 少了这句，调用方会照着"规则被篡改"去排查，白烧半天

## 六、BFF 注入（P0 第二半）

`sgcc_bff.py` 新增规则源机制：`_review/rules_source_v2.json`（46 条、15 字段、39322 字节，
由 `_review/make_rules_source.py` 从函数导出并校验指纹一致）。

### 三道防线，少一道就出假绿

| # | 防线 | 不做会怎样 |
|---|---|---|
| ① | 规则源解析失败 → 抛 `CliError`，**绝不退回内嵌** | 客户把规则改坏了，界面照样给漂亮结论，还看不出来用的是旧规则 |
| ② | 快照/缓存指纹含规则指纹 | 改了规则、输入没变 → 命中旧快照 → "改了却没变"，或反之 |
| ③ | 规则指纹原样传给函数 | 指纹对不上时无人知晓，留痕链断了 |

①实测：`broken.json → CliError[rules_source_invalid]`、`empty.json` / `notlist.json` 同样报错、
合法文件正常注入。
②实测：`fp(无规则)=ac0562bb…` 与 `fp(有规则)=470089bd…` 不同；**无规则源时指纹与改造前完全一致**，
老快照继续有效，不为兼容性付重算代价。

### 端到端演示（真实 HTTP）

```
预热：warmup ok；presnap 6/6 全 live，41548 ms

① 基线（规则源 = V2）
   POST /api/judge/by-code {"code":"YC"}
   _source=snapshot  rule_source=input  rule_set=V2  sha=e80fd7b21492dc44
   decided=9  counts={RESPONDED:8, NOT_RESPONDED:1, UNCERTAIN:16, NEED_HUMAN:21}  fail_rows=[10]

② 改一条规则（行10 判定式 → 恒真，版本名 V2-DEMO1）
   GET /api/judge/snap  → all_fresh=False，宜昌 stale=True
   POST /api/judge/by-code {"code":"YC"}
   _source=live  rule_set=V2-DEMO1  sha=547438f9228905be
   counts={RESPONDED:9, NOT_RESPONDED:0, …}  fail_rows=[]

③ 函数版本核对
   apemind function get sgcc-rule-judge  → 版本：v5，共 5 个（没有产生 v6）

④ 还原规则源
   POST /api/judge/refresh {"codes":["YC"]} → ok, wall 8028ms
   POST /api/judge/by-code → rule_set=V2  sha=e80fd7b2…  counts 回到 NOT_RESPONDED:1  fail_rows=[10]
```

**②→④ 之间没有任何发布动作**，结论却实质变了 —— 这是 P0 要的那件事。
